# Changelog

All notable changes to Frick framework packages are recorded here. The format is loosely based on [Keep a Changelog](https://keepachangelog.com/) and the versioning policy lives in [`docs/versioning.md`](docs/versioning.md).

Each package version is independent — a release header documents which packages moved and by how much.

## Unreleased

- **`@fricken/design` + `@fricken/design-web` + `@fricken/protocol`:** Automated accessibility + localization test suite (FR-104). Locks in the FR-101 a11y contract and FR-103 localization hooks as regression-catching invariants rather than spot checks — adding a control, icon, or error code without its required affordance now fails a test. **Accessibility (`packages/design-web/src/a11y-suite.test.tsx`):** the `frickIconNames` contract is complete, duplicate-free, resolves in *both* the native and frick fallback packs (asserted as exactly the contract — no extra/missing keys), and every rendered glyph is decorative (`aria-hidden`, `focusable="false"`); interactive controls (`Button`, `IconButton`, `TextField`, `TextArea`, `Toggle`, `SegmentedControl`, `Composer`, `WorkspaceListItem`, `WorkspaceShell` nav) render as real, keyboard-operable native elements with accessible names/roles, `aria-invalid` error signalling, and managed selected/pressed/current state; graphical components (`PresenceDot`, `ProgressRing`) expose role + name with bounded/clamped value semantics; and a CSS contract check proves every interactive selector carries a `:focus-visible` ring, the UA default is suppressed for pointer focus, and `prefers-reduced-motion` neutralizes transitions/animations. **Contrast (`packages/design/tests/a11y.test.ts`):** strengthened with a contract-integrity block asserting unique pair ids, in-range thresholds, and that every `SEMANTIC_CONTRAST_PAIRS` entry resolves to a real hex token in all 12 resolved themes (mode × density × brand) — on top of the existing per-theme WCAG-AA enforcement. **Localization (`packages/protocol/tests/localization-suite.test.ts`):** the English `defaultErrorMessages` table covers every `FRICK_ERROR_CODES` entry **and** has no stale entries (guards future codes added without a message), every default renders to a non-empty, non-bracketed string, the full fallback chain (region tag → base language → English default → envelope message → bracketed code) resolves in the documented order so the UI never renders empty, and interpolation (`{token}` templates, well-known fields, unknown-token passthrough, non-primitive drop, explicit-param override) plus function messages and the localizer lifecycle are all covered. Test-only change — no runtime/library surface moves; kept consistent with the existing node + `renderToStaticMarkup` setup (no new dev dependencies).
- **`@fricken/server`:** Configurable retention policies for growth-prone, auto-pruned tables (FR-68). The durable retention windows that were previously only settable ad-hoc through `StoreOptions` are now first-class, env-driven `FrickConfig` fields wired into the store, alongside the already-config-driven `platformEventsRetentionMs`. New config: `idempotencyKeyRetentionMs` (`FRICK_IDEMPOTENCY_KEY_RETENTION_MS`, default 24h — the durable `idempotency_keys` cleanup window, distinct from the lookup-time `idempotencyReplayWindowMs`; per-tenant `retentionMs` settings still win), `devtoolsEventsRetentionMs` (`FRICK_DEVTOOLS_EVENTS_RETENTION_MS`, default 1h — the `devtools_events` feed), and `expiredSessionRetentionGraceMs` (`FRICK_EXPIRED_SESSION_RETENTION_GRACE_MS`, default 0 — the forensics grace before an expired `auth_sessions` row is pruned; non-negative). The prune mechanics are unchanged — only the windows move — and leaving every variable unset reproduces today's exact defaults, so this is fully additive and backward-compatible. Positive-integer validation for the retention windows, non-negative for the grace, both fatal at startup via `FrickConfigError`. Documented in `docs/operations.md` (env-var table + a new "Configuring retention windows" note). New `apps/server/tests/retention-config.test.ts`; per-stream opt-in retention (FR-145) remains a separate `streamRetention` surface.
- **`@fricken/server`:** Opt-in server-side device binding for sessions (FR-32). The Principal's `deviceId`/`replicaId` were already derived from the `auth_sessions` row rather than the client's Hello frame, so the server never *trusted* a client-claimed device. The remaining gap was re-auth on device change: a still-valid session token presented from a *different* device during the Hello handshake was accepted. A new opt-in toggle `FrickLimits.bindSessionDevice` (env `FRICK_BIND_SESSION_DEVICE`, default **OFF**) closes it — when enabled, the gateway compares the Hello frame's `deviceId` *and* `replicaId` against the values the session token is bound to and, on mismatch, rejects the Hello with an `auth.unauthenticated` Nack (`details.reason = "sessionDeviceMismatch"`) and closes the socket (1008) so the client re-authenticates and mints a session bound to its own device. Default-off preserves existing FrickSwift/web flows exactly; the binding values are still always server-derived, so a client can never spoof another device's identity regardless of the toggle. New tests: `apps/server/tests/ws-session-device-binding.test.ts` (default-off connects on mismatch; flag-on accepts a matching device and rejects mismatched device/replica) plus env-parsing coverage in `apps/server/tests/limits.test.ts`.
- **`@fricken/design` + `@fricken/design-web`:** Cross-platform accessibility contract (FR-101). The design system now ships an enforced, documented a11y contract (see [`docs/accessibility.md`](docs/accessibility.md)). **Contrast:** `@fricken/design` adds a pure, dependency-free contrast core (`contrastRatio`, `relativeLuminance`, `parseHexColor`, `isHexColor`, `WCAG_CONTRAST`) plus a declarative `SEMANTIC_CONTRAST_PAIRS` table and `checkContrastPairs(semantic)`. A new suite enforces WCAG AA on every foreground/background pair across all 12 resolved themes (mode × density × brand), which surfaced and fixed real deficiencies: light-mode `success`/`info`/`warning` tones are darkened to clear 4.5:1 on the page, dark mode gains lighter `success`/`warning`/`danger`/`info` tones (status colors are now mode-aware), the `frickenChat` primary action darkens to `#3a5cbf` so white text clears AA on the fill, and `frickenChat` stops overriding the outgoing chat bubble (it inherits the mode-aware mint treatment so bubble text stays legible in dark mode). Token artifacts (web CSS/TS, Swift, Kotlin, JSON) regenerated. **Icon names:** `@fricken/design-web` exposes a frozen, documented `frickIconNames` contract with an `isFrickIconName` guard; every name is guaranteed to resolve in both the native and frick fallback icon packs. **Keyboard + focus:** a single visible `:focus-visible` ring (`--frick-focus-ring-*` tokens) is applied to every interactive control, with the UA default suppressed for pointer focus. **Reduced motion:** a `@media (prefers-reduced-motion: reduce)` block neutralizes transitions/animations (and the new typing-indicator animation), and the composer remains Enter-to-send. **Screen-reader labels:** roles/accessible names on interactive + graphical components are now test-covered. New tests: `packages/design/tests/a11y.test.ts`, `packages/design-web/src/a11y.test.tsx`.
- **`@fricken/bench`:** Latency (FR-97) and throughput + resource-growth (FR-98) benchmark suites, built on the FR-96 load harness. Both extend the existing `bench/` package rather than forking a new one, reusing its `summarizeLatency` percentile math and adding a shared server-spin-up/handshake helper (`bench/src/server-target.ts`). **Latency (`runLatency`, `pnpm bench:latency`)** measures one sample per iteration across the core paths and emits machine-readable JSON (`tool: "frick-latency-bench"`) with p50/p90/p99 per path: `httpRequest` (authenticated HTTP GET round-trip), `wsAppend` (WS stream append → durable Ack), `objectFanout` (one client upserts an object, a second subscribed client receives the broadcast Delta), `catchUp` (Subscribe → first StreamPage over a seeded backlog), and `reconnect` (open WS + Hello → HelloAck). Flags: `--iterations`, `--catch-up-backlog`, `--http-url`/`--ws-url`, `--pretty`. **Throughput + resource growth (`runThroughput`, `pnpm bench:throughput`)** drives a sustained append/upsert workload across N concurrent WS connections and emits JSON (`tool: "frick-throughput-bench"`) with completed ops/sec (appends, upserts, combined) plus a `resources` section sampling `process.memoryUsage()` (rss/heapUsed), SQLite db byte size + per-table row counts (`stream_events`, `objects`, `idempotency_keys`), and the idempotency-cache row count before vs after, with deltas. Flags: `--connections`, `--ops-per-connection`, `--upsert-ratio`, `--no-await-acks`, `--seed`, `--http-url`/`--ws-url`, `--pretty`. Both default to an in-process server on an in-memory SQLite store; `--http-url`/`--ws-url` drive an external server (growth is omitted there since the `store` isn't reachable). The CLI gains `latency`/`throughput` subcommands (no subcommand still defaults to the FR-96 load harness). New programmatic exports `runLatency`/`runThroughput` (+ config/result types) and `parseLatencyConfig`/`parseThroughputConfig`. Correctness stays in the regular suites — the harnesses only measure. New `apps/server/tests/bench-suites.test.ts` runs a tiny config of each end-to-end and asserts the JSON result shape (percentiles present, every path exercised, resource growth sampled).

- **`@fricken/protocol` + `@fricken/design-web`:** Localization hooks for error-code messages and component labels (FR-103). The wire protocol is unchanged — error *codes* (`storage.conflict`, `auth.unauthenticated`, …) stay stable and untranslated; turning a code into a localized human string is now a presentation-layer concern with a proper mechanism. `@fricken/protocol` adds `ErrorLocalizer` (plus the `localizeErrorCode` one-shot), a complete English `defaultErrorMessages` table covering every `FRICK_ERROR_CODES` entry, and the `FrickMessageTable` / `FrickMessage` / `FrickMessageParams` types. Apps inject partial per-locale tables keyed by tag (`es`, `fr-CA`, …); resolution falls back region-tag → base language → English default → the envelope's own `message` → bracketed raw code, so the UI never renders empty. Messages can be `{token}` templates (interpolated from an envelope's `details`, with unknown tokens left intact) or functions for pluralization/grammar. `@fricken/design-web` adds `FrickLabelsProvider` / `useComponentLabels` for localizing built-in component chrome (English defaults, partial overrides merge over them); the workspace inspector's previously hard-coded "Close" button now reads from it and accepts an inline `closeInspectorLabel` prop that wins over the provider. New tests: `packages/protocol/tests/localization.test.ts`, `packages/design-web/src/labels.test.tsx`.
- **`@fricken/bench` (new):** Reusable synthetic load harness (FR-96). A new private `bench/` workspace package drives configurable synthetic load against a Frick server and emits a single machine-readable JSON result to stdout for CI/trend comparison. By default it spins up an in-process `createFrickServer` on an ephemeral port backed by an in-memory SQLite store, registers N synthetic users (each dev-logs-in over HTTP, opens a WS connection, Hello-handshakes, and optionally subscribes to its conversation stream), then drives per-user object upserts and stream appends while recording per-operation latency. The JSON result (`schemaVersion: 1`, `tool: "frick-load-harness"`) carries the resolved config, env, total wall-clock duration, per-operation summaries (count, errors, min/max/mean/p50/p90/p99 latency, throughput/sec) and aggregate totals. Run via `pnpm load:harness` with flags (`--users`, `--appends-per-user`, `--object-writes-per-user`, `--seed`, `--no-subscribe`, `--pretty`) or env fallbacks (`FRICK_LOAD_*`); `--http-url` + `--ws-url` drive an already-running external server instead of spinning one up. Exposed programmatically as `runLoad(config)` / `parseLoadConfig(argv, env)` for the upcoming benchmark stories (FR-97–100). Correctness is left to the regular suites — the harness only measures. New `apps/server/tests/load-harness.test.ts` runs a tiny config end-to-end and asserts the JSON result shape.
- **`@fricken/server`:** Opt-in refresh-token / short-access-token split (FR-33). Sessions were a single long-lived token at one configured TTL. Setting `identityProviders.refresh` (`{ accessTokenTtlSeconds?, refreshTokenTtlSeconds?, rotateOnRefresh? }`) turns on a split: every provider sign-in (apple/google/oidc/email) now mints a short-lived **access token** (the session, default 15 min) *and* a long-lived **refresh token** (default 30 days, returned as `refreshToken` / `refreshTokenExpiresAt` alongside the session). A new `POST /auth/refresh` exchanges a valid refresh token for a fresh access token and, by default, **rotates** the refresh token (the presented token is revoked and a fresh one returned, so a replayed token is rejected on its second use); set `rotateOnRefresh: false` to reuse the presented token. `POST /auth/refresh/revoke` revokes a refresh token (idempotent, always 200). Refresh tokens are opaque high-entropy values stored only as a SHA-256 hash (new `auth_refresh_tokens` table, migration `0018_refresh_tokens`, SQLite + Postgres parity) and bound to the sign-in's `(tenant, user, device, replica)`. Apple consent-revoke and password-reset now also revoke a user's refresh tokens. Fully **backward compatible**: with `refresh` unset, sign-ins keep their single-session shape and the `/auth/refresh*` routes return 404. New `RefreshTokenStore` (`store.refreshTokens`), exported `RefreshProviderConfig`, and `tests/refresh-tokens.test.ts`.

- **`@fricken/server`:** Cascade grant scoping to search results + blob access (FR-71), with thorough authz tests (FR-73). Cross-user sharing grants now extend past direct object reads (FR-116) and stream/projection reads (FR-70) to two more surfaces, reusing the existing grant-lookup/decide pipeline. **Search:** the `POST /search` per-hit filter now runs the full per-record read pipeline — object hits go through `canSubscriberReadObjectRecord` (app policy hooks may tighten the tenant-wide allow to a deny, a grant relaxes it back for the grantee); stream hits pass the FR-70 `cascadeGrantLookup` into `assertCanSubscribe`; projection hits (which have no fail-closed baseline) surface to a grantee only when an active cascade grant on the record id == projection key exists, otherwise staying deny-by-default behind app policy. **Blobs:** `assertCanReadBlob(principal, ownerId, hooks, blobId?, cascadeGrantLookup?)` now relaxes an `ownerMismatch` deny when the principal holds an active read grant on the record whose id == the blob's `blobId` — so a blob stored under a shared record id is readable by its grantee across `GET /blobs/:id`, `…/content`, and the derivative routes; `tenantMismatch` and policy-hook denies are never relaxed. All paths are tenant-scoped and revocation-aware: a revoked or left grant removes search/blob visibility on the very next request, and the cost short-circuits to the prior behavior when no grant/policy applies. **Jobs:** out of scope — the job store is keyed by `(tenant_id, job_type)` with no per-user/per-record association and no user-facing read route (enqueue is admin-gated), so grant visibility does not apply. New `tests/cascade-search-blob-authz.test.ts` covers cascade visibility for object/stream search hits and blobs plus revoke and leave-share, across allow, deny, and cross-tenant paths.

- **`@fricken/server`:** Multi-key push credential rotation with an overlap window (FR-61). Rotating the at-rest encryption key for stored push credentials (APNs/FCM/Web Push, wrapped AES-256-GCM in `tenant_settings`) previously required re-saving every tenant in lockstep — a blob written under the old key was unreadable the instant `FRICK_PUSH_CRED_KEY` changed. `FRICK_PUSH_CRED_KEY` is now strictly the *primary* key (all new writes encrypt under it), and an optional `FRICK_PUSH_CRED_KEY_PREVIOUS` (comma-separated base64 32-byte keys) names outgoing keys kept readable during the overlap. `decryptCredential` tries the primary first, then each previous key in order, falling through GCM auth-tag mismatches and only reporting `push.credentials.corrupt` once every key fails; blank/wrong-size entries in the previous list are skipped. Operators roll tenants forward at their own pace, then drop `FRICK_PUSH_CRED_KEY_PREVIOUS` to retire the old key. No API/signature changes (env-var only). New `tests/push-credentials-rotation.test.ts`.

- **`@fricken/server`:** Privacy-safe logging + auth/data-lifecycle audit events (FR-69). The structured logger's sensitive-field scrubber now also redacts message / stream-event bodies and payloads (`body`, `payload`, `ciphertext`) and rounds out the credential set (`cookie`, `signature`, `digest`, `passphrase`, `otp`, `mnemonic`, `seed`) on top of the existing token/password/secret/key patterns — benign hash-shaped fields (`schemaHash`, `entryHash`, `previousHash`) stay readable and `credentials` containers are still recursed into, not wholesale-redacted. New exports `redactSensitiveFields(fields)` and `isSensitiveFieldName(key)` let call sites scrub log/audit `detail` payloads defensively. Auth and data-lifecycle actions now emit tamper-evident rows on the shared admin-audit hash chain: `auth.signup`, `auth.login` (allow + `deny` on bad credentials), `auth.logout`, `account.export`, and (in the email-identity router) `auth.password_reset.issued` / `auth.password_reset.completed`. The actor is fingerprinted from the subject userId (`u:<12 hex>`) so a row never carries the raw identity, the subject is the `target`, and audit `detail` is scrubbed through `redactSensitiveFields` so a token or body can never enter the chain. `account.delete` was already audited. New `tests/privacy-logging-audit.test.ts`.

- **`@fricken/protocol` + `@fricken/server` + `@fricken/cli`:** Structured diagnostics snapshot data model and CLI surface (FR-76, FR-77). `@fricken/protocol` now exports a canonical `DiagnosticsSnapshot` type — schema identity + compatibility verdict, active subscriptions, stream cursors, pending appends, recent ack/nacks, recent (redacted) error envelopes, connection state, cache metadata, sync timing, and negotiated capabilities/limits — plus `redactDiagnosticsContext` (name-based secret masking for unstructured error context) and `DIAGNOSTICS_VERSION`. `@fricken/server` exports `assembleDiagnosticsSnapshot(store, opts)`, which builds the snapshot from a live `FrickStore`: schema/migration compatibility, idempotency cache metadata, caller-requested stream-cursor probes, and recent error envelopes sourced from the DevTools event feed (HTTP ≥400 and `*.failed`/`*.dead_lettered`/`*.error` kinds), each run through `redactDiagnosticsContext` so secrets never reach the snapshot. Gateway-only surfaces (live connection/subscription/pending-append state) are passed in via `runtime` and omitted when absent. `@fricken/cli` adds `frick inspect diagnostics` — emits the full snapshot from a local DB with no HTTP server, accepting optional `stream:streamId` positional args to probe specific cursors. New exports: `DiagnosticsSnapshot` (and member types), `redactDiagnosticsContext`, `REDACTED_DIAGNOSTICS_VALUE`, `DIAGNOSTICS_VERSION`, `assembleDiagnosticsSnapshot`, `AssembleDiagnosticsOptions`, `DiagnosticsCursorProbe`, `DiagnosticsRuntime`. Tests cover secret redaction (`packages/protocol/tests/diagnostics.test.ts`, `apps/server/tests/diagnostics-snapshot.test.ts`) and the CLI surface.
- **`@fricken/server`:** Pluggable/configurable password hashing with lazy scrypt migration (FR-35). A new `FrickPasswordHasher` interface (`hash` / `verify` / `needsRehash`) backs account credentials, with an **Argon2id** implementation (`@node-rs/argon2`) now the default and a `scrypt` implementation kept for back-compat. Stored hashes are self-describing — each carries an algorithm tag (`argon2$…`, `scrypt$N$r$p$keylen$salt$digest`) so `verify` dispatches on the tag and migration detects older formats; pre-FR-35 rows (separate `password_salt` column + untagged digest) are reconstructed as `legacy-scrypt$…` and still verify. On every successful login a hash in an older/weaker format than the active hasher is transparently re-hashed and persisted (the salt is embedded, so the legacy salt column is left empty); re-hash failures never block login. Selectable via `FRICK_PASSWORD_HASHER` (`argon2` | `scrypt`) / `FrickConfig.passwordHasher` / `StoreOptions.passwordHasher` (also accepts a pre-built hasher for custom parameters), defaulting to `argon2`. Account-creation and reset flows now `await` the (now genuinely async) hashing so the row is persisted before the session is used. New `tests/password-hasher.test.ts`.

- **`@fricken/server`:** Opt-in per-stream retention for the durable stream-store (FR-145). Stream events are source-of-truth application data, so the store keeps everything forever by default; `StoreOptions.streamRetention` (a `{ [streamType]: { maxAgeMs?, maxEvents? } }` map) prunes only the named stream types. `maxAgeMs` drops events older than the cutoff; `maxEvents` keeps the newest N per `(tenant, stream, streamId)` via a correlated subquery (verified identical on SQLite and Postgres). Runs on a background timer (only armed when a policy is declared, default 15 min) on the same schema-gated one-shot-then-interval shape as the other retention sweeps, and clears on `close()`. Cursor-safety is documented as the operator's responsibility — bounds must exceed the slowest subscriber's catch-up window. New exports: `StreamRetentionPolicy`, `StreamRetentionPolicies`, `StreamRetentionPruneResult`, and `StreamStore.pruneRetention`.

- **`@fricken/server`:** Multi-node-safe job + platform-event claiming (FR-28). On Postgres, two worker nodes hitting the shared database could previously claim the same row (the `UPDATE … WHERE id IN (SELECT … WHERE status='ready')` outer re-check doesn't re-test status, so both nodes' subqueries selected the same ids). The claim subqueries now use `FOR UPDATE SKIP LOCKED` on Postgres (`FOR UPDATE OF d SKIP LOCKED` for the platform-event delivery join) so concurrent claimers take disjoint sets; SQLite serializes writers on one connection and omits the clause. Also fixes a latent Postgres gap: `JobStore.enqueue` now uses `INSERT … RETURNING id` so the generated job id round-trips (it was 0 on Postgres). Verified with `tests/pg-job-claim-concurrency.test.ts` — 8 concurrent claimers over 60 jobs, each claimed exactly once. Projection workers are unaffected: they recompute idempotent per-tenant read models (same key → same value), so multi-node recomputation is safe by construction.

- **`@fricken/server`:** Shipped a production `RedisClusterBus` (FR-27) for multi-node horizontal-scale fan-out. Implements `FrickClusterBus` over a single Redis pub/sub channel with msgpack-encoded (binary-safe) envelopes, the `originNodeId` loop guard, and `setSubscribedTenants` wire-level tenant filtering — exact parity with `MemoryClusterBus`. Uses two connections (a subscribe-mode connection can't `PUBLISH`); `createRedisClusterBus({ url })` wires both from `ioredis` (an optional dependency, imported lazily), or construct `RedisClusterBus` with any client satisfying the small `RedisBusClient` surface. New exports: `RedisClusterBus`, `createRedisClusterBus`, `randomNodeId`, `RedisBusClient`, `RedisClusterBusOptions`, `CreateRedisClusterBusOptions`. Validated against real Redis in `tests/redis-cluster-bus.test.ts` (fake-client unit coverage always runs; the ioredis integration runs when `FRICK_REDIS_URL` is set).

- **`@fricken/server`:** Shipped a Postgres full-text search adapter (FR-24). The `FrickSearchAdapter` seam is now async (`upsert`/`delete`/`query` return promises) so engines that can't run synchronously plug in; the SQLite FTS5 adapter wraps its sync store, and the new `createPgFtsSearchAdapter` uses Postgres's native full-text search — the `search_indexes.text_tsv` generated `tsvector` column with a GIN index, matching via `@@ plainto_tsquery('simple', …)` and ranking with `ts_rank`. Field filters map `json_extract(fields,'$.k')=v` → `(fields::jsonb->>'k')=v`. Relevance is adapter-defined (ts_rank high-is-better vs bm25 low-is-better; route leaves the score untouched). New exports `createSqliteFtsSearchAdapter`, `createPgFtsSearchAdapter`; new `tests/pg-search.test.ts`; CI `test:pg` widened.

- **`@fricken/server`:** Verified the blob metadata + derivative stores run on the Postgres adapter (FR-122). `BlobStore.create` and `BlobDerivativeStore.record` used SQLite's `INSERT OR REPLACE` (→ portable `INSERT … ON CONFLICT(<pk>) DO UPDATE`); BYTEA content round-trips through the adapter. Blob *bytes* remain a separate, synchronous `BlobBytesDriver` seam — Postgres deployments serve bytes via the filesystem driver (`FRICK_BLOB_DRIVER=filesystem`); a Postgres-native BYTEA bytes driver needs an async bytes interface (tracked under FR-9). New `tests/pg-blobs.test.ts`; CI `test:pg` widened. This completes the per-store-family Postgres adapter slices (FR-119–122); wiring Postgres into `createFrickServer` itself (async construction + porting the SQLite-bound devtools/search/platform-event subsystems off `rawDb`) remains the horizontal-scale follow-up.

- **`@fricken/server`:** Verified the tenant/admin/runtime stores (tenant, tenant-settings, admin-audit, push-registration) run on the Postgres adapter (FR-121). Two portability fixes: `TenantStore.ensure` used SQLite's `INSERT OR IGNORE` (→ portable `INSERT … ON CONFLICT DO NOTHING`), and `AdminAuditStore.record` relied on `lastInsertRowid` for the chain id (→ portable `RETURNING id`, which the SqlDriver surfaces as `lastInsertRowid` on both backends). New `tests/pg-tenant-admin.test.ts`; CI `test:pg` widened.

- **`@fricken/server`:** Verified the identity stores (account, session, password-reset, grant, invitation) run on the Postgres adapter (FR-120). Two portability fixes the conformance suite surfaced: `AccountStore` identity lookup used SQLite's `COLLATE NOCASE` (→ portable `LOWER(handle) = LOWER(?)`, works on both backends), and `GrantStore.isEmptyAsync` compared `EXISTS(...)` against `0`/`1` (SQLite returns an integer, Postgres a boolean → now treats it as truthy). New `tests/pg-identity.test.ts`; CI `test:pg` widened to run it.

- **`@fricken/server`:** Shipped the Postgres implementation of the `SqlDriver` async storage seam (FR-119). `PgSqlDriver` runs the store SQL on a `pg` pool — rewriting `?`→`$n`, normalizing params (`boolean`→`0|1`, `undefined`→`NULL`, `Uint8Array`→`Buffer`), parsing `BIGINT` back as JS numbers, and mapping `rowCount`→`changes` (with `RETURNING id`→`lastInsertRowid`). Transactions check out a dedicated client (BEGIN/COMMIT/ROLLBACK, nested calls reuse the outer tx). New async `createPgSqlDriver({ databaseUrl, supportedSchemaRevision })` connects + runs the framework migrations and returns a ready driver. Verified against real Postgres 16: the object, stream, and idempotency stores run **unmodified** on the adapter (their `ON CONFLICT … DO UPDATE` / `RETURNING` SQL is already dialect-neutral). New exports: `PgSqlDriver`, `createPgSqlDriver`, `rewritePlaceholders`. The CI `test:pg` job now also runs the adapter conformance suite. Note: wiring this into `createFrickServer` itself still needs async construction + porting the SQLite-bound devtools/search/platform-event subsystems off `rawDb` (FR-121).

- **`@fricken/server`:** Added projection-author ergonomics helpers (FR-134) — pure DX sugar over the `FrickProjection` API: `listProjectionObjects<T>(ctx, type)` (typed `ctx.store.listObjects(ctx.tenantId, type)`), `singleChange(key, value)` (build a one-row `ProjectionApplyResult`), and `projectionSourceObjectTypes(projections)` (the distinct object source types across projections, for boot bootstrap). Completes the FR-127 app-author SDK epic.

- **`@fricken/server`:** Shipped per-tenant recurring-job fan-out (FR-132). `eachTenant({ includeArchived?, filter?, payload? })` builds a `FrickRecurringJob.resolveTargets` that enumerates the tenant ledger so a recurring job enqueues once per tenant per tick — the framework owns the "enumerate live tenants" loop (it holds the ledger); the app supplies only an optional predicate and per-tenant payload. Excludes archived tenants by default. New exports: `eachTenant`, `EachTenantOptions`.

- **`@fricken/server`:** Shipped a multi-tenant active-tenant switch helper (FR-131). `deriveSiblingSession(store, { fromSessionToken, tenantId, ttlSeconds, ... })` mints a new session scoped to `tenantId` while reusing the caller's `userId`/`deviceId`/`replicaId` from their live session, registering the target tenant in the ledger (`ensureTenant`, default on) — the generic "switch tenant" re-mint apps were hand-rolling. Throws `SourceSessionNotActiveError` when the source token has no live session (surface as `401`). Membership/authorization stays the app's responsibility (run it before calling). Token generator and `now` are injectable for tests. New exports: `deriveSiblingSession`, `SourceSessionNotActiveError`, `DeriveSiblingSessionOptions`, plus the `StoredSession` / `CreateSessionInput` types.

- **`@fricken/server`:** Shipped a declarative RBAC policy-hook builder (FR-133). `makeRbacPolicyHook(matrix)` turns a `role × action × resource-type` matrix into a tightening-only `FrickPolicyHook`: each per-(role, action) rule is `"all"`, `"none"`, `{ allow: [...] }`, or `{ deny: [...] }`, and the hook denies a governed pair that the rule forbids while offering no opinion on ungoverned actions/roles/principals (so the framework default and other hooks still stand). Role derivation stays app-supplied via `matrix.resolveRole(principal)` — the framework deliberately does not bake in a userId→role convention. New exports: `makeRbacPolicyHook`, `RbacMatrix`, `RbacResourceRule`.

- **`@fricken/server`:** Shipped an app-route helper kit (FR-128) so `ServerOptions.appRoutes` handlers — which receive a raw `(req, res)` with no framework context — stop re-implementing the same glue. New exports: `setCors` / `handlePreflight` (configurable CORS + preflight), `sendJson` (JSON response with CORS applied), `readJsonBody` (parses the body, returns `{}` when empty, and bounds buffered size to `DEFAULT_MAX_JSON_BODY_BYTES` = 1 MiB, throwing `JsonBodyTooLargeError` past the cap), `matchPath` (a `:param` matcher returning URL-decoded captures), and `authenticateRequest` (bearer token → live session → framework `Principal`; role/RBAC mapping stays with the app). Generalised from aquariusyacht's `runtime/http.ts`.
- **`@fricken/server`:** Shipped a stock image blob processor + magic-byte sniffer (FR-130), so apps stop re-implementing image-upload validation. New exports: `sniffImageFormat(preview)` (recognises PNG/JPEG/GIF/WebP from the leading bytes, defense-in-depth against a lying `Content-Type`) and `imageBlobProcessor({ maxBytes?, message?, id?, matches? })` — a `FrickBlobProcessor` factory whose `validate` rejects empty, oversize, non-`image/*`, and unrecognised uploads before they reach storage and attaches `{ format }` to the blob's extracted metadata. Defaults to matching every upload (`matches: {}`) so non-images are actively rejected; cap defaults to `DEFAULT_MAX_IMAGE_BYTES` (10 MiB).
- **`@fricken/server`:** Expired `auth_sessions` rows are now swept automatically (FR-42). They were always filtered out on read but never deleted, so the table grew unbounded. The store runs an expired-session prune once at startup and then on a 15-minute background timer, alongside the existing `idempotency_keys`, `devtools_events`, and `platform_events` prune passes. A session is eligible the moment it expires; embedders can keep a forensics grace window via `createFrickServer({ expiredSessionRetentionGraceMs })` or disable the timer with `expiredSessionPruneIntervalMs: 0` (the one-shot at startup still runs). New `SessionStore.pruneExpired(cutoffIso?)`.
- **`@fricken/server`:** Added an admin session-revocation route `POST /_frick/admin/sessions/revoke` (FR-34), so operators stop deleting `auth_sessions` rows by hand. Revoke by `userId` (every session for that user, optionally scoped to one `tenantId`) or by a single `sessionToken`: the matching rows are deleted (blocking future requests) and any currently-connected WebSocket for those sessions is live-disconnected with close code `1008`, so a revoked client can't keep streaming on an already-open socket. Returns `{ revoked, disconnected }`; a request naming neither target returns `400 sync.protocolError`. Fail-closed audit-logged as `sessions.revoke`. Backed by a new `SyncGateway.closeSessionsForUser(userId, tenantId?)` companion to the existing `closeSession(token)`.
- **`@fricken/server` / `@fricken/protocol`:** Object **deletes** now live-push to subscribed sync clients (FR-142). Previously every other mutation (object upserts, stream appends) fanned out over the sync gateway but `store.deleteObject` did not — so other connected clients kept the deleted row until their next cold refetch. `deleteObject` now emits an `objectDelete` store write-event (only when a row actually existed), which the gateway fans out as a `Delta` frame carrying the removed id two ways: as a tombstone object record (the current Swift/Android SDKs refetch on any object delta and drop the now-absent row) and as a new optional `removed: { type, id }[]` list on `DeltaPayload` (a forward-looking client drops the ids directly, no refetch). Deletes are tenant-scoped and forwarded over the cluster bus (`objectDeletes` envelope) so peer nodes drop the rows for their own subscribers. The `removed` field is additive and absent on deltas with no deletions, so existing clients are unaffected. Retires RangerCRM's `@fricken/server` dist patch for delete fan-out.

### Swift — product-schema sync resilience

- **FrickSwift:** `FrickClient` now accepts the full app schema identity (`schemaId`, `schemaRevision`, `schemaHash`) plus an injected `FrickSchemaDescriptor`, and threads those values into sync Hello payloads, capability metadata, HTTP schema guards, and packed Snapshot/Delta decoding. Product-schema apps no longer have to rely on the foundation schema id/descriptor when decoding app-defined object or stream frames.
- **FrickSwift:** `FrickSyncSocket` replays active subscriptions after reconnect and continues to buffer subscribe/upsert/presence/signal frames issued immediately after `connect()` until the WebSocket opens, preserving FIFO ordering behind Hello.
- **FrickSwift:** `FrickClient.fetchObjects` now decodes rows individually and skips malformed rows with a log notice, so one incompatible or corrupt object row does not abort the entire fetch result.

### Server — sharing grants cascade to streams + projections

- **`@fricken/server`:** A sharing grant on an object record now cascades READ access to the derived primitives keyed by that record's id, within the same tenant: the stream whose `streamId` equals the granted record id, and the projection rows whose subscribe/read `key` equals that id (FR-70). The cascade runs after the baseline policy + app hooks + object-record grant relaxation and only ever flips a deny to allow (never the reverse); it is strictly read-only (`stream.append` and writes are never relaxed), tenant-scoped, and fails closed when there is no resolvable row id (e.g. a whole-projection subscribe with no `key`). Revoking the grant restores the underlying deny. New `assertCanSubscribe` cascade parameter backed by `FrickCascadeGrantLookup` / `relaxWithCascadeGrants` in authz and `GrantStore.hasActiveGrantForRecordId`. See [`docs/threat-model.md`](docs/threat-model.md).

### Server — encrypted Web Push payloads (RFC 8291)

- **`@fricken/server`:** The Web Push adapter now encrypts notification content per RFC 8291 (Message Encryption for Web Push) using the `aes128gcm` content encoding (RFC 8188), so the title/body/data reach the browser Service Worker instead of an empty wake-up (FR-60). When a `PushSubscription` registration carries the browser's `keys.p256dh` + `keys.auth`, the adapter generates an ephemeral P-256 keypair, derives the shared secret via ECDH, runs the RFC 8291 / RFC 8188 HKDF key + nonce derivation, AES-128-GCM encrypts a single record, and frames the body as `salt(16) || rs(4) || idlen(1) || keyid` + ciphertext with `Content-Encoding: aes128gcm` and `Content-Length` alongside the existing VAPID `Authorization` header. A fresh ephemeral key and salt are used per send; an over-4096-octet body returns `push.payloadTooLarge` without dispatch. Registrations without subscription keys keep the backward-compatible empty-body path. New export `encryptWebPushPayload` from `@fricken/server/push/web-push-adapter`. Multi-key rotation of the encryption material (FR-61) and APNs/FCM are unchanged. See [`docs/push-adapters.md`](docs/push-adapters.md).

### Server — per-user blob quota

- Added a configurable per-principal `(tenantId, ownerId)` total-bytes blob quota (`maxBlobBytesPerPrincipal` limit + `FRICK_MAX_BLOB_BYTES_PER_PRINCIPAL` env var, also per-tenant overridable via `tenant_settings`). Uploads that would push an owner's summed blob bytes over the cap are rejected with the new `blob.quotaExceeded` error envelope (HTTP 413) before any metadata row or bytes are written. `GET /blobs?ownerId=<id>` now returns the owner's `usage` (`usedBytes`/`quotaBytes`) alongside the list. The default cap is effectively unlimited, so existing deployments are unchanged until they opt in. (FR-56)

### Server — per-record authz on object subscriptions

- **`@fricken/server`:** Object subscriptions are now authorized **per record** (FR-116). The initial snapshot and every live object delta are filtered for each subscriber with the same policy-hook + sharing-grant pipeline that gates individual `object.read` calls, layered on top of the existing tenant scoping. A tightening-only policy hook that denies `object.read` for a principal now removes those rows from that subscriber's snapshot and live stream, and a grant on a record makes exactly that record visible to the grantee — so different subscribers on the same object type can see different row sets. Per-record evaluation short-circuits to the prior allow-all behavior (no per-row cost) when no policy hook is registered and no sharing grant has ever been issued. The wire protocol, `@fricken/core`, the HTTP object read authz, and the grant CRUD API are unchanged. Unblocks per-record customer-portal visibility over live sync (aquarius-os AQ-63).

### Server — stream cursor query API

- **`@fricken/server`:** Added `GET /streams/:type/:id/cursor` returning `{ headSequence, count }` — a cheap tenant-scoped head probe (max sequence + event count, no payloads decoded) — and extended `GET /streams/:type/:id` with `?since=<sequence>`, which returns only events with `sequence > since` in ascending order (paginated by `?limit=`), so a client can resume a stream from a known position without replaying history. `?before=` paging is unchanged; a non-numeric `since` returns `400 stream.invalidCursor`. Backed by the new `StreamStore.head` helper (surfaced as `FrickStore.streamHead`) plus the existing `StreamStore.read` forward-read (FR-117). Unblocks cursor-based stream resume for downstream consumers.
### Server — filesystem blob-bytes driver

- **`@fricken/server`:** Blob bytes can now be stored on the local filesystem instead of SQLite. A new `FRICK_BLOB_DRIVER` selector (mirroring the FR-21 `FRICK_DB_DRIVER` pattern) chooses the blob-bytes backend: `sqlite` (the default, unchanged — bytes stay in the `blob_content` table) or `filesystem` (FR-53). Under the `filesystem` driver, blob bytes are written under `FRICK_BLOB_STORAGE_PATH` in tenant-isolated, id-keyed files; identifiers are hashed into the on-disk path so a crafted blob id can never escape its tenant directory, and one tenant can never read, write, or delete another tenant's bytes. Blob *metadata* always stays in SQLite under either driver, and the blob HTTP route contract is unchanged.
- The `filesystem` driver fails fast at startup: selecting it without a `FRICK_BLOB_STORAGE_PATH` is rejected at config validation, and a path that is not a writable directory is rejected when the driver is constructed. Writes go through a temp-file + atomic rename so a concurrent reader never observes a partial file. New internal storage seam `BlobBytesDriver` (`SqliteBlobBytesDriver` / `FilesystemBlobBytesDriver`) with `write` / `read` / `delete` / `exists`; `BlobStore` gains `deleteContent` / `hasContent`. Object-storage (S3, FR-54), derivatives offload (FR-55), and quotas (FR-56) remain separate follow-ups. See [`docs/operations.md`](docs/operations.md).

### Server — unified session TTL + auth-attempt limiter across all providers

- **`@fricken/server`:** Every identity-provider sign-in (Apple, Google, generic OIDC, and email/password) now mints its session with the single configured `FRICK_SESSION_TTL_SECONDS` lifetime instead of a hardcoded 30-day TTL (FR-29). There is now one TTL knob for all session types — demo-auth, password login/signup, and provider sign-ins all honor the same value (default 7 days). Apps that relied on the old fixed 30-day provider session must set `FRICK_SESSION_TTL_SECONDS` (or `config.sessionTtlSeconds`) explicitly to keep a 30-day lifetime.
- The identity-provider verify endpoints (`/auth/apple/verify`, `/auth/google/verify`, `/auth/oidc/:id/verify`) and the email password-reset endpoints (`/auth/email/forgot-password`, `/auth/email/reset-password`) now run through the **same** fixed-window auth-attempt limiter that already protected `/auth/login` and `/auth/signup` (`maxAuthAttemptsPerWindow` / `authRateLimitWindowMs`), closing the gap where an attacker could sidestep the password-login ceiling by hammering a provider or reset route. Provider-verify routes bucket by client IP; `forgot-password` buckets by the submitted email and `reset-password` by the submitted token. When tripped these routes return `429` with a flat `{ "error": "rate_limited", "retryAfterSeconds" }` body and a `Retry-After` header (the existing password routes keep their structured `rateLimit.exceeded` envelope). New exported types: `IdentityAuthThrottle`; `IdentityRouterOptions` gains `sessionTtlSeconds` and `authThrottle`. No change to provider verification behavior or to the session/auth response shapes on the success path. See [`docs/operations.md`](docs/operations.md) and [`docs/threat-model.md`](docs/threat-model.md).

### Server — live push for server-originated object/stream writes

- **`@fricken/server`:** Object upserts and stream appends made **server-side** through the store — a background job or app command route calling `store.upsertObject` / `store.upsertObjectWithPolicy` / `store.appendEvent` directly — now live-push to already-subscribed sync clients as `Delta` frames, closing the gap where such writes persisted and updated projections/search but never reached connected subscribers until the slower cursor resync (FR-114). HTTP `PUT /objects/...` writes, which previously did not broadcast at all, now also push live. Deltas remain tenant-scoped (a subscriber only sees writes in its own tenant).
- Broadcasting is now driven by a single funnel: the store emits a write-change notification on every successful object upsert / stream append, and the sync gateway is the sole consumer that fans it out (reusing the same `publishObjects` / `publishStreamEvent` path, including cluster-bus forwarding to peer nodes and the SSE bridge). The gateway frame handlers and the HTTP append route no longer broadcast inline, so a single write produces exactly one delta per subscriber — no duplicates. The broadcast carries the stored (post-merge) object state. New `@fricken/server` exports: `FrickStoreWriteEvent`, `FrickStoreWriteListener`, and `FrickStore.setWriteListener`.
- One observable nuance for a client that writes and is also subscribed: the canonical `Delta` for its own write may now arrive before that write's `Ack` (the broadcast fires inside the store write, ahead of the handler's ack). The two are independent on `@fricken/core` (the delta updates the cache; the ack clears the pending write), so ordering is not contractual and convergence is unaffected. No wire-protocol or `@fricken/core` change. See [`docs/operations.md`](docs/operations.md).

New exports: from authz — `FrickPolicyHook`, `FrickPolicyInput`, `FrickDecision`, `FrickDecisionReason`, `FrickAction`, `Principal` (types) plus the `deny` helper and `ALLOW` constant (values); from the blob pipeline — `FrickBlobProcessor`, `FrickBlobValidateContext`, `FrickBlobValidationResult`, `FrickBlobProcessContext`, `FrickBlobProcessResult`, `FrickBlobProcessorRegistry`. ### Server — generic OIDC provider routing

- **`@fricken/server`:** `createFrickServer({ identityProviders })` now accepts an `oidc` array of generic OpenID Connect providers, so apps can plug in any standards-compliant issuer (Okta, Auth0, Microsoft Entra, Keycloak, …) for sign-in alongside the existing Apple / Google / email providers (FR-30). Each provider is `{ id, issuer, clientId, audience?, jwksUri? | discovery, claimMappings? }` and mounts `POST /auth/oidc/:providerId/verify`. The client obtains an `id_token` from the issuer and POSTs it; Frick verifies signature + `iss` + `aud` (defaulting to `clientId`) + expiry with `jose` against the provider's JWKS — resolved either from a directly-configured `jwksUri` or by fetching the issuer's `<issuer>/.well-known/openid-configuration` discovery document (`discovery: true`) and reading its `jwks_uri`. When discovery is used the document's own `issuer` must match the configured issuer (defense against a hijacked well-known endpoint). An optional request `nonce` is checked when supplied. Standard claims (`sub`, `email`, `name`, `preferred_username`) plus any `claimMappings.extra` (`{ "<UserField>": "<claim>" }`) populate the app-owned User object; first sign-in runs the same `onFirstSignIn` hook the other providers use (now `provider: "oidc"` with `providerId`), and a normal bearer session is minted exactly like the Google path. The verified `sub` is stored on the new `oidcSubject` User field as a per-provider composite `"<providerId>:<sub>"`, so two issuers reusing the same subject never alias onto one account. Session TTL/limiter unification across providers remains separate follow-up work (FR-29). New exports: `OidcProviderConfig`, `OidcClaimMappings`, `OidcProviderRuntime`, `VerifiedOidcIdentity`, `VerifyOidcOptions`, `OidcDiscoveryDocument`. No change to Apple, Google, or email behavior. See [`docs/operations.md`](docs/operations.md).

### Server — self-service account deletion

- **`@fricken/server`:** Added an authenticated `DELETE /account` route (with `POST /account` accepted as an alias) that erases the calling principal's OWN account — its owned object records, all of its sessions in the tenant, and its `auth_accounts` row (FR-67). Object deletion reuses the export's ownership convention (`DEFAULT_OWNER_FIELDS` = `ownerId` / `userId` / `createdBy`, override via `AccountDeleteOptions`) and the tenant-scoped store, so another principal's or another tenant's data is never touched — not even a cross-tenant record whose owner field collides with the caller's `userId`. The caller's live gateway connection is closed and the session stops authenticating immediately. Unauthenticated requests return `401`; the `no-store` response reports `accountDeleted`, `deletedSessions`, and per-type `deletedObjects` counts. This is the data-subject "delete my own data" surface, distinct from the operator-driven `/_frick/admin/data-subject` route.
- Apps can cascade product-specific deletion with an `onAccountDelete(principal, result)` hook on `createFrickServer` options; it runs after the framework default commits, receives the framework's result, and owns its own tenant/owner scoping. Every deletion appends an `account.delete` row to the admin audit hash chain. New exports `deleteAccountData` and types `AccountDeleteOptions` / `AccountDeleteResult` / `OnAccountDelete`. Retention policies (soft-delete, legal-hold) remain out of scope (tracked separately). See [`docs/operations.md`](docs/operations.md) and [`docs/threat-model.md`](docs/threat-model.md).

### Server — self-service account data export

- **`@fricken/server`:** Added an authenticated `GET /account/export` route that returns the calling principal's OWN data as a single JSON bundle, grouped by object type, scoped to the principal's tenant (FR-66). A record is included when one of its `ownerId` / `userId` / `createdBy` fields (`DEFAULT_OWNER_FIELDS`) equals the principal's `userId`; tenant isolation is enforced by the tenant-scoped store, so another tenant's records never appear even when an owner field matches. ### Server — grantee leave-share / self-revocation

- New `POST /share/grants/:id/leave` route lets the grantee of a share self-revoke ("leave") their own grant, returning `{ grant }` with the revoked row. Previously only the grant owner could revoke (via `DELETE /share/grants/:id`), so a recipient had no way to drop their own access (FR-72). The new route is grantee-only: any other caller — including the owner — gets a tenant-isolated `404`, and `DELETE` remains owner-only. Self-revocation reuses the existing idempotent revoke path, so leaving an already-revoked grant returns the existing revoked row. Documented in `docs/operations.md` and `docs/threat-model.md`.

### Design — token validation hardening

- `@fricken/design` validation (`pnpm design:check`, run as part of `pnpm design:generate` / `pnpm verify:generated`) now catches more classes of token mistakes and fails the build on any of them:
  - **Off-scale spacing/radius:** literal `semantic.spacing` / `semantic.padding` / `semantic.corner` values (including density overrides) must be members of the declared `primitive.space` / `primitive.radius` scales, not merely on the 4-point grid.
  - **Circular aliases:** alias cycles are now detected statically across every mode/density/brand layer combination, not just the single default resolve, so a cycle hidden in an override layer is reported up front with its full chain.
  - **Missing icon mappings:** component `icon.*` aliases that point at a key absent from `icons` are flagged with the offending component path instead of silently emitting a dangling glyph name.
  - **Color contrast:** the resolved semantic palette is checked for WCAG 2.1 contrast across all modes/brands — body-text pairs against AA (4.5:1) and the action-button label pair against AA-large (3:1).
  - **Raw styling literals:** a new linter scans the handwritten `packages/design-web/src/components.css` and rejects raw color literals (hex / `rgb()` / `hsl()`) and fractional `opacity` values in component rules, steering them to `var(--frick-*)` tokens. Definitions in the `--frick-*` bridge layer and structural numerics (`0`/`1` opacity, grid/`minmax`/`%`/breakpoints) are exempt.
- Tokenized the one pre-existing raw literal this surfaced: the disabled-state `opacity: 0.48` in `components.css` now references a new `--frick-opacity-disabled` bridge variable (mirroring `primitive.opacity.disabled`). No generated artifact or rendered value changed.

### Server — CORS subdomain/suffix wildcard origins

- `FRICK_ALLOWED_ORIGINS` (and the `allowedOrigins` config override) now accept subdomain wildcard entries of the form `<scheme>://*.<host>` (e.g. `https://*.example.com`) alongside the existing allow-all `*` and exact-origin entries. A wildcard matches any non-empty subdomain prefix over the same scheme and port (`https://app.example.com`, `https://a.b.example.com`) but not the apex host (`https://example.com`) unless that exact origin is also listed. Large multi-tenant deployments no longer need to enumerate every per-tenant origin. Matching is shared by the HTTP preflight/response path and the WebSocket upgrade `verifyClient` check; wildcard-matched requests reflect the concrete request origin (with `Vary: Origin`), never the pattern string. Malformed entries (bare-host wildcards like `https://*`, mid-host wildcards, multiple wildcards, or non-origin strings) are rejected at config load with `FrickConfigError`. The production default remains the closed empty allowlist.

### Server — per-principal connection cap

- `@fricken/server` now enforces a per-principal concurrent WebSocket connection cap in addition to the existing global `maxWebSocketConnections` cap. The new `FrickLimits.maxConnectionsPerPrincipal` field (default `64`) is keyed by `(tenantId, userId)` and enforced at connect when a bearer token is present, otherwise at the `Hello` handshake. Over-cap connections receive a structured `rateLimit.exceeded` Nack (with `details.limit: "maxConnectionsPerPrincipal"`) and are closed with code `1013`, without affecting other principals. Configurable via `createFrickServer({ limits })` or the `FRICK_MAX_CONNECTIONS_PER_PRINCIPAL` env var (an explicit `limits` override wins over the env var). Counters are in-process and reset on restart, consistent with the single-node model.

### Server — outbound email adapter surface

- `@fricken/server` now exports a documented outbound email surface, mirroring the push-adapter convention. New exports from the main entrypoint: the `FrickEmailAdapter` / `FrickEmailMessage` / `FrickEmailDelivery` / `FrickEmailContext` interfaces, `createFrickEmailRouter` (+ `FrickEmailRouter` and its option/helper types), `createFrickResendEmailAdapter` (the Resend reference adapter, reading `RESEND_API_KEY`), and `createFrickTestEmailAdapter` (the in-memory test sink). The Resend adapter is also reachable via the `@fricken/server/email/resend-adapter` subpath, matching `@fricken/server/push/apns-adapter`.
- `identityProviders.email` gained an opt-in `outbound` config (`EmailOutboundConfig`): supply an adapter + `defaultFrom`, and the framework dispatches the password-reset email (`/auth/email/forgot-password`, when a `resetUrl` builder is provided) and a first-sign-in welcome email (`/auth/email/signup`, when `welcome` is set) through it. URL composition stays in app code. Sends are best-effort — a failed delivery is logged and audited in the DevTools event feed but never fails the originating auth request. The existing `onPasswordResetRequested` hook still fires and coexists with framework-managed dispatch, so apps that want full control keep their seam.

### Bug Fixes

- **Swift SDK:** `FrickSyncSocket.sendFrame` now buffers frames into the existing pending queue when the WebSocket task isn't open yet, instead of throwing `notConnected`. This fixes a race where consumers issuing `subscribeObject` / `subscribePresence` / `setPresence` / `clearPresence` / `subscribeProjection` immediately after `FrickClient.connectSync()` (which schedules `openSocket()` on a detached Task) would intermittently fail. Buffered frames flush in FIFO order right after the hello handshake lands.

### Swift SDK — per-app schema hash override

- `FrickClient.init(...)` now accepts a `schemaHash: String` parameter (default `FrickSchema.schemaHash`). Apps with a custom protocol schema can pass their own hash so wire-level guards — response envelopes (`requireCompatibleSchema(expected:)`), the `X-Frick-Schema-Hash` header, the sync Hello frame, and cache-metadata bootstrap — compare against the app's hash rather than the generated foundation default. `FrickSyncSocket.init(...)`, `FrickClientCapabilities.defaultIOS(...)`, and `FrickCacheMetadata.currentSchema(...)` gained matching defaulted `schemaHash:` parameters so the override threads end-to-end. Unblocks RangerCRM (and other consumers) from the previous workaround of aligning their server's `schema.hash` to the foundation hash.

### Swift SDK — auto reset-cache on session swap

- `FrickClient` now auto-resets the on-disk cache when an auth call installs a session for a *different* `userId` than the one currently in the store (RCRM-45). All sign-in / sign-up entry points (`signInWithApple`, `signInWithEmail`, `signUpWithEmail`, `signInWithGoogle`, `signUp`, `login`, `devLogin`) and `restoreSession` funnel through a private `installSession` helper that compares incoming-vs-current `userId` and only clears storage on a real swap. Consumers no longer have to call `resetCache()` before swapping users to avoid the session-scope-mismatch guard; same-user reauth and first-sign-in are unaffected. The helper also clears when this client build's `schemaHash` has drifted from the persisted cache row (a same-`schemaId`/same-revision upgrade `verifyCacheCompatibility` does not catch). Persisted user-scope drift across a process boundary (relaunch, or sign-out → sign-in as a different user) stays the job of `verifyCacheCompatibility`, which `fetchObjects` / `connectSync` run — `installSession` deliberately leaves that metadata intact so the guard can still fire (FR-3).

- Removed most chat-specific React helpers from the public `@fricken/react`

### Protocol

- Frame kinds: `hello`, `hello-ack`, `subscribe`, `unsubscribe`, `append`, `signal`, `object-upsert`, `projection-delta`, plus heartbeat and error envelopes.
- `schemaRevision: 1` baseline with capability negotiation in the hello handshake.
- Shared `FrickErrorEnvelope` over HTTP and WebSocket paths.
- Native schema artifact generator emits Swift and Kotlin constants from the TS source of truth.
- Baseline fixtures plus a drift check (`pnpm verify:generated`) guard the generated outputs.
- Schema linter module surfaces shape violations for app authors.

### Server (`@fricken/server`)

- Migration runner with checksum-pinned `frick_migrations` table; refuses to boot on drift or unknown future revisions.
- Sync gateway with hello handshake, capability negotiation, frame-size caps, per-tenant limits, heartbeat, presence TTL, and bounded subscription/pending-append queues.
- Multi-tenant isolation threaded through every storage method, request path, and admin route.
- Authorization decisions with typed reason codes; deny-by-default for unknown actions; tenant-scope checks on writes; conversation-membership and blob-ownership enforcement.
- Object versioning with `versionPrecondition` enforcement and `ObjectUpsert` conflict envelopes over the sync socket.
- Typed projection registry with delta broadcasting; conversation inbox re-expressed as a projection.
- Job worker with backoff, dead-letter queue, lifecycle inspect routes, and admin trigger endpoint.
- Push notification router as a job handler with device registrations and admin delivery.
- SQLite FTS5 search adapter wired into store writes with an admin rebuild route.
- Blob derivative storage, synchronous upload validators, and a `blob.process` job handler.
- Backup and restore: NDJSON dump generator with schema-tagged header; restore reader refuses schema drift.
- Per-tenant settings store with admin routes; HTTP and WS paths resolve limits per request.
- DevTools event store with retention pruning; emits events on HTTP, WS, and job lifecycle.
- Compliance: data-subject export and erase endpoints, hash-chained admin audit log with `verifyChain`.
- App registry and hello-driven app routing; `/_frick/inspect/apps` and admin schema-lint route.
- Operational surface: graceful shutdown with in-flight tracking, health/ready/inspect routes, structured logger with redaction defaults, child loggers, per-request log lines, metrics module, idempotency cache with retention and row caps, CORS enforcement, admin bearer auth.
