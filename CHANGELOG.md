# Changelog

All notable changes to Frick framework packages are recorded here. The format is loosely based on [Keep a Changelog](https://keepachangelog.com/) and the versioning policy lives in [`docs/versioning.md`](docs/versioning.md).

Each package version is independent — a release header documents which packages moved and by how much.

## Unreleased

### Security

- **`@fricken/server` — multi-region federation audit hardening (`apps/server/src/cluster/region-redis-bus.ts`, `region-bus.ts`, `region-router.ts`, `region-failover.ts`; findings multi-region-1, multi-region-2, multi-region-3, multi-region-4, multi-region-6, multi-region-7):** Fixed 6 confirmed audit findings in the cross-region transport, each with a regression test.
  - **multi-region-1 (authz, critical) — federated `RegionEnvelope`s crossed the WAN with zero authentication:** an inbound envelope is re-injected into the local cluster bus and fanned out to subscribers on its self-asserted `tenantId` alone, so any party able to PUBLISH to the cross-region channel (a compromised/rogue region, a leaked or shared Redis credential, a misconfigured broker) could forge stream events, object deletes, presence, and signals for **any tenant in every subscribing region** — defeating tenant isolation across the WAN. `RedisRegionBus` now authenticates the channel at the application layer: a new per-deployment shared secret (`regionSecret` on `RedisRegionBusOptions` / `createRedisRegionBus`) signs every outbound frame with **HMAC-SHA256** over the encoded envelope plus a per-frame nonce + timestamp; inbound frames are verified **timing-safe before any handler dispatch** and dropped+logged if unsigned, forged, stale, or replayed. Backward-compatible: with no secret the wire/behavior is unchanged (single-region / memory fabric). Documented in `docs/multi-region.md` → "Cross-region trust boundary" that the channel is a cross-tenant trust boundary that SHOULD additionally run over a mutually-authenticated transport (mTLS / private network / per-region ACLs) even with the HMAC.
  - **multi-region-2 (race-condition, high) — failover promotion candidates were only the local health map's keys:** `RegionFailoverCoordinator.#promoteAwayFrom` chose the new home from `#health.keys()`, so a genuinely healthy region that was never explicitly reported into the coordinator was silently excluded as a target, and coordinators that observed different health subsets could promote the same key to different homes (non-deterministic, split-brain on ownership). Promotion now draws candidates from the **full known region universe** — the union of the ownership map's regions (new `StaticRegionOwnership.knownRegions()`), a new optional `configuredRegions` coordinator option, and reported health — with regions absent from the health map considered `healthy` by default, so every region computes the identical lowest-id winner from identical ownership + configured-region inputs. Determinism still requires every coordinator be fed the same inputs (documented in `docs/multi-region.md` → "Failover determinism").
  - **multi-region-4 (stability, medium) — malformed-but-decodable cross-region payload re-injected as a null/garbage envelope:** a payload that msgpack-decoded to a non-`RegionEnvelope` (e.g. `{foo:'bar'}`, a bare string, `null`) passed the `originRegionId === regionId` loop guard and was re-published into the intra-region bus, where peers decoded `null`/garbage and threw in the gateway dispatch. The decoded value is now structurally validated (non-null object, string `originRegionId`, well-formed inner `envelope` with a `kind`) in `RedisRegionBus.#onMessage` **and** defensively in `FederatingClusterBus` before re-injection — malformed frames are dropped + logged.
  - **multi-region-6 (dos, low) — `FederatingClusterBus` re-injected every inbound cross-region envelope ignoring `setSubscribedTenants`:** the intra-region tenant filter lives on the inbound hop, but federated envelopes were re-published via `local.publish` (never filtered), so a region serving zero subscribers for a tenant still paid full WAN-receive + intra-region re-publish for it. `FederatingClusterBus` now snapshots its served-tenant set and short-circuits re-injection of inbound envelopes whose `tenantId` is not served (the media-placement sentinel tenant is always passed through; pass-through until the gateway declares a served set, for back-compat).
  - **multi-region-7 (correctness, low) — `MemoryRegionProxy.onProxiedWrite` returned a stale-closure unsubscribe:** the returned closure called `this.#detach` (re-read at dispose time), so after a re-registration (h1 then h2) disposing h1's unsubscribe tore down h2 — the live home applier — silently dropping all proxied writes. The closure now captures the specific detach it installed and only clears the field if it still points at that detach.

- **`@fricken/server` — call-authorization & media-lifecycle audit hardening (`apps/server/src/calls/`, `apps/server/src/authz.ts`, sync gateway CallCommand dispatch; findings calls-token-1, calls-media-1, calls-authz-1, calls-signal-1, calls-isolation-1, calls-correctness-1, calls-stability-1, sfu-media-1..7):** Fixed 14 confirmed audit findings in the calls subsystem, each with a regression test.
  - **calls-token-1 / sfu-media-1 (authz, high) — SFU join token never verified:** `issueJoinToken` minted an HMAC nonce documented as the produce/consume credential, but nothing verified it. Added `SfuMediaPlaneAdapter.verifyJoinToken(callId, actor, token)` — re-derives `HMAC(secret, callId:userId:deviceId:expirySeconds)` with `crypto.timingSafeEqual` and rejects forged or expired tokens. A `token` field is threaded from `CallCommand` → control plane → `connectTransport`/`produce`/`consume` (additive protocol field) so the credential — expiry + identity binding — is now enforced.
  - **calls-media-1 / sfu-media-2 (authz/isolation, high) — cross-participant transport hijack:** transports were scoped to the call's router with no owner binding, so any joined participant could connect/produce/consume on another's transport. The adapter now records the owning `(userId,deviceId)` at transport creation; connect/produce/consume assert the actor owns the transport (produce only on own send, consume only onto own recv).
  - **calls-authz-1 (authz, high) — createCall had no membership check:** any user could ring anyone and bind a call to an arbitrary `conversationId`. Added `assertCanCreateCall` (reusing the tenant-membership reader + policy-hook machinery): creator + every invitee must be tenant members, and a new `call.create` policy-hook action lets an app enforce conversation membership.
  - **calls-signal-1 (isolation, high) — WebRTC signal relay ungated:** the `WebRTCSignal`/`keyEpoch` relay (keyed by callId) was an unconditional ALLOW, so any tenant user could inject/read SDP/ICE/E2EE-key signals into a call they weren't in. Added `CallSignalAuthorizer`: `signal.send`/`signal.read` on a `WebRTCSignal` now require call participant/invitee/creator membership (`CallControlPlane.isSignalMember`), wired into the WS gateway (send + subscribe) and the HTTP signal POST/GET routes. Non-call signals are unaffected.
  - **calls-isolation-1 (isolation, medium) — call records ignored appId:** call records/events landed in the tenant default app namespace regardless of the connection's app (FR-153). `appId` is now threaded through `CallActor` → every control-plane store read/write/`appendEvent` (writes via app-aware `upsertObjectWithPolicy`); the gateway stamps `actor.appId = #appIdFor(client)`.
  - **sfu-media-3 (resource-leak, high) — transports leaked on leave + every rejoin:** `leaveCall` now closes the leaving participant's transports/producers/consumers, and `issueJoinToken` is idempotent per `(callId,userId,deviceId)` — a rejoin replaces the prior transports instead of leaking a fresh pair each time.
  - **sfu-media-4 (correctness, medium) — P2P maxParticipants never enforced:** `createCall`/`joinCall` now consult `mediaPlane.describe().maxParticipants` and reject calls/joins that exceed it (distinct active users; a same user+device rejoin is free).
  - **sfu-media-5 (stability, medium) — poisoned worker-init promise:** `#ensureWorker` no longer caches a rejected init promise, so a transient `createWorker` failure no longer bricks the backend — the next call retries a fresh worker.
  - **sfu-media-6 (stability, medium) — no worker 'died' handler:** the mediasoup worker's `'died'` event now drops the dead worker and invalidates its routers so callers re-allocate. An injectable `createWorker` factory makes both paths testable without building the native module.
  - **sfu-media-7 (crypto, medium) — no empty/weak shared-secret guard:** `SfuMediaPlaneAdapter` (tokenSecret) and `P2PWebRTCAdapter` (TURN shared secret) now reject secrets shorter than 16 bytes at construction, failing closed instead of issuing forgeable credentials.
  - **calls-correctness-1 (correctness, medium) — creator could never join their own call:** the room creator (no invite row) is now an implicit, always-accepted member; `joinCall` issues them a media grant and `acceptInvite` is a no-op success.
  - **calls-stability-1 (stability, low) — `#finalizeEnd` cast a possibly-undefined room:** guarded against a delete/end race so it fails closed (`callNotFound`) rather than persisting a corrupt `CallRoom` record.
  - New/updated regression tests in `apps/server/tests/{sfu-media-plane,calls-control-plane,calls-wire,p2p-media-plane,mediasoup-sfu-backend}.test.ts`. All changes backward-compatible; existing server tests stay green.
- **`@fricken/core` — Security: E2EE call-crypto audit hardening (`packages/core/src/e2ee.ts`; findings crypto-e2ee-1..5,7):** Six confirmed audit findings in the FR-85/FR-156/FR-158 E2EE seam fixed, each with a regression test (`packages/core/tests/e2ee.test.ts`, `e2ee-production.test.ts`, `e2ee-asymmetric.test.ts`). **crypto-e2ee-1 (transition-window correctness, high):** `CallKeyEpochManager` now ages out the previous epoch from a **local-clock demotion timestamp** stamped at supersession (`rotate`/`adopt`), not from the epoch's `createdAt` — so an epoch that was current longer than the window is kept for the full transition window (no instant drop of in-flight frames) and a remote announcer's clock skew can no longer make a departed-member key linger past the window. **crypto-e2ee-2 (replay TOCTOU, medium):** `SFrameCipherTransform.decrypt` serializes all decrypts of one `(epoch,sender)` stream so the `seen()` pre-screen and post-auth `check()` commit are atomic, and the return is gated on `check()` — two concurrent decrypts of the same counter can no longer both succeed (a replay is accepted at most once). **crypto-e2ee-3 (pre-auth allocation DoS, medium):** replay windows are allocated **only after AEAD authentication** (a flood of forged, attacker-chosen `senderId`s allocates nothing), the number of tracked senders per epoch is **LRU-bounded** (`maxSendersPerEpoch`, default 256), and per-epoch derived-key/counter/replay state is **pruned** when an epoch ages out of the manager. **crypto-e2ee-4 (unauthenticated key-epoch announcements, medium):** `AsymmetricKeyDistributor` now **signs** each announcement with the sender's long-term identity key (new injectable `SignatureProvider`, default `WebCryptoSignature` ECDSA-P256; `SenderKeyDirectory`/`MapSenderKeyDirectory` resolves signer keys) and **verifies it against the directory before adopt** — a relay or any directory-readable party can no longer forge an epoch the victim adopts; the per-recipient wrap AAD now also binds the **sender device id + ephemeral public key** so a blob can't be spliced under a different sender. Unsigned legacy mode is preserved when no sender directory is configured. **crypto-e2ee-5 (monotonic-counter poisoning, medium):** `adopt()` and both distributors' `poll()` reject an **implausibly large epoch jump** (`maxEpochJump`, default 1024) without advancing the monotonic `#highestSeen`, so one forged high-`epochId` announcement can no longer permanently wedge all future legitimate epochs; adoption stays gated on successful unwrap/authentication. **crypto-e2ee-7 (senderId truncation, low):** the constructor now **rejects** a `senderId` outside `[0, 2^32)` instead of silently `>>> 0`-truncating it, surfacing a caller misassignment that would otherwise collapse two senders onto one nonce stream (AES-GCM key+nonce reuse). All changes additive and back-compatible; existing E2EE callers and tests unchanged. Core gate green (118 tests, 0 failures).
- **`@fricken/server` — blob pipeline + orphaned-blob GC audit hardening (FR-161 remediation; findings blob-gc-1..6, tenant-app-isolation-6):** Fixed seven confirmed audit findings in `apps/server/src/blobs/`, every one fail-safe toward keeping data.
  - **Fixed (blob-gc-1, data-loss/availability):** `blob.process` derivative persistence was **fire-and-forget** — `BlobDerivativeStore.record()` became async but `persistDerivative` was still `: void` and called without `await`, so the job reported **completed before the derivative bytes were durably written** (completed jobs never retry → silent loss of thumbnails/transcodes/moderation sidecars) and a `record()` rejection became an **unhandled promise rejection that can crash the worker**. `persistDerivative` is now `async` and awaited; any failure surfaces in the handler's try/catch → the job correctly reports **failed + retryable**.
  - **Fixed (blob-gc-2 == tenant-app-isolation-6, resource-leak):** GC only ever swept the **`_default`** app, so non-default apps' orphans leaked forever in a multi-app server. `appId` is now threaded end-to-end: `FrickJobContext.appId` (stamped by the worker from the job row), `runOrphanedBlobGc({ appId })`, the declared-ref scan, `listOldestFirstPage`/`deleteContent`/`deleteMetadata`, and the `BlobIsReferencedHook` args. The recurring sweep fans out **one pass per (tenant, app) that actually holds blobs** (`BlobStore.listAppIdsWithBlobs`), with the recurring scheduler now app-scoping the idempotency key. Still opt-in + grace-windowed; single-app servers are byte-for-byte unchanged.
  - **Fixed (blob-gc-3, race/data-loss):** **TOCTOU** — the declared-ref set is a per-pass snapshot, so an aged orphan **re-attached to a freshly written object mid-pass** could be deleted while live. Immediately before each delete the GC now **re-validates against live state** (`recheckOrphanBeforeDelete`): the blob must still be present, still past the grace window, still unreferenced by a **targeted live declared-ref re-scan**, and still not hook-protected — otherwise the delete is skipped.
  - **Fixed (blob-gc-4, DoS):** the pass loaded **every** `blob_metadata` row (and every ref-declaring object) into heap at once (OOM on large tenants). The scan is now **keyset-paginated** (`BlobStore.listOldestFirstPage`, default page 500) so heap stays bounded regardless of tenant size; `listAllOldestFirst` is no longer on the GC path.
  - **Fixed (blob-gc-6, data-loss):** the `isReferenced` hook return was coerced with truthiness (`if (protectedByHook)`), so a non-boolean/`undefined`/throwing hook (an easy app bug) silently **deleted a referenced blob**. The GC now deletes **only when the hook returns the explicit boolean `false`**; `true`, any non-boolean, or a thrown error is treated as **referenced/unknown → keep** (logged, never deleted).
  - **Fixed (blob-gc-5, DoS):** `imageBlobProcessor` bounded only **encoded** byte length — a small but huge-dimension PNG/WebP/JPEG/GIF (decompression bomb) was handed straight to the (often app-supplied) decoder. Added a header-only `parseImageDimensions` and a **decoded-pixel ceiling** (`maxPixels`, default `DEFAULT_MAX_IMAGE_PIXELS` = 40 MP) enforced at `validate` **and** before the generator runs at process time; oversized inputs are rejected with a clear error and never decoded. Dimensions are now exposed in extracted metadata.
  - New regression tests: `apps/server/tests/blob-gc-audit.test.ts` (multi-app sweep, TOCTOU re-reference, paginated scan, hook fail-safe coercion), `apps/server/tests/image-decompression-bomb.test.ts` (dimension parsing + bomb rejection at validate/process), `apps/server/tests/blob-processor-job-persistence.test.ts` (awaited persistence → failed+retryable on `record()` rejection). All additive and backward-compatible; existing server tests stay green.
- **`FrickSwift` (native Swift client) — sync-socket audit hardening (security + correctness fixes):** Fixed seven confirmed findings in the WebSocket sync client (`packages/swift/Sources/FrickSwift/`), all minimal and backward-compatible. **Security / DoS:**
  - **native-swift-3 — NaN/Inf float → `Int(Double)` trap (remote DoS):** `FrickMsgPackValue.intValue` converted a decoded `.double` via `Int(v)` with no finiteness guard; `Int(.nan)`/`Int(.infinity)` is a fatal trap, so a single crafted inbound frame `[<NaN float>, payload]` hit `parts[0].intValue` (frame kind) and hard-crashed the receive loop. Now guards `isFinite` and uses `Int(exactly: v.rounded(.towardZero))` (and `Int(exactly:)` for ints), returning `nil` instead of trapping — also covers the FR-144 `decodeObjectRemoval` `tuple[0].intValue` trap site.
  - **native-swift-4 — unbounded `reserveCapacity` (memory DoS):** `readArray`/`readMap` reserved capacity straight from a 16-/32-bit length header before reading any element, so a tiny frame declaring a ~`UInt32.max` array length forced a multi-gigabyte allocation (OOM). The reservation is now clamped to the bytes remaining in the buffer (each element is ≥1 byte), so a truncated-but-huge length throws `.truncated` fast without the giant allocation; well-formed large arrays/maps still decode unchanged.
  - **native-swift-6 — `join()` media token broadcast to every events observer (credential exposure):** `handleCallCommandResult` resumed the awaiting caller AND yielded the full `FrickCallCommandResult` — including `mediaGrant.token` (a short-lived participant-scoped media credential) — onto the shared broadcast `events` stream, where any observer (logger/telemetry sink) could capture it. The caller still gets the grant via the awaited return value; the broadcast copy now has `mediaGrant` stripped (`redactingMediaGrant()`).
  - **native-swift-2 — in-flight continuation leak on socket drop (hang/resource leak):** `handleDisconnect` tore down and reconnected without draining `pendingResponders`/`pendingCallResponders`; an already-sent request frame is not replayed on reconnect, so an `upsertObject`/`callCommand` (`join`/`leave`/`setMediaState`/…) awaited across a mid-flight reconnect hung forever (call UI spinner stuck, task leaked until `close()`). Now drains both responder maps on disconnect, resuming each with the new `FrickSyncSocketError.connectionDropped` so awaiters fail fast and can retry.
  - **native-swift-1 — single-consumer `events` race (silent data loss):** `events` returned the same backing `AsyncThrowingStream` on every access; an `AsyncThrowingStream` is single-consumer, so with 2+ `FrickStore`/`FrickProjectionStore`/`FrickCallSession` loops on one socket each inbound delta reached only one iterator (round-robin) — a delta for `Account` could be consumed and discarded by a `ContactStore` iterator. Reworked to **broadcast/fan-out**: one internal sink, a per-subscriber continuation registry, and `events` now vends a fresh child stream per caller so every consumer receives every event; `close()` finishes all subscribers; cancelled iterators deregister via `onTermination`.
  - **native-swift-5 — rows deleted while disconnected aren't dropped on reconnect (stale/possibly access-revoked data):** a row deleted server-side during an offline window generates no `.objectsRemoved` event — it's simply absent from the reconnect snapshot — and the merge-only apply path left it lingering. Added a distinct `.objectsSnapshot` event (the `Snapshot` frame no longer masquerades as `.objectsDelta`); `FrickStore` and `FrickCallSession` now **reconcile** to a snapshot (drop cached rows of a carried type that are absent from it) instead of pure-merging, while incremental `.objectsDelta` still merges. An empty/sibling-type snapshot is treated as non-authoritative for a store and never clears it.
  - **native-swift-7 — `flushPending` re-decodes every queued frame for a telemetry label (hot-path perf):** the reconnect flush re-parsed every buffered (potentially large) frame just to recover its `kind` for the sent-frame counter. The `FrickFrameKind` is now captured on `PendingSocketAppend` at enqueue time and read directly on flush — no re-decode.
  Regression tests added: `Tests/FrickSwiftTests/FrickMsgPackHardeningTests.swift` (codec NaN/Inf + reserveCapacity DoS), plus new cases in `FrickSyncSocketTests.swift` (events broadcast to multiple/pre-connect consumers, close finishes subscribers, upsert/callCommand fail-fast on disconnect, media-grant not broadcast, flush records kind without re-decode), `FrickStoreTests.swift` (snapshot drops offline-deleted rows, merge-in-place reconcile, empty/sibling snapshot no-clear), and `FrickCallSessionTests.swift` (snapshot drops offline-removed participant). Swift gate green (174 tests, 0 failures; was 151).
- **`@fricken/server` — Security/Fixed: storage-layer isolation & atomicity audit fixes (server-storage-1/2/3/4/7, tenant-app-isolation-5):** Closed six storage-domain audit findings in `apps/server/src/storage/`, all backward-compatible with SQLite+Postgres parity.
  - **server-storage-2 / tenant-app-isolation-5 (Security — cross-app idempotency clobber):** `idempotency_keys` PRIMARY KEY omitted `app_id`, so two apps sharing a `(tenant, replica, request)` tuple clobbered each other's idempotency row via `INSERT … ON CONFLICT`, silently bypassing stream-append exactly-once dedup (one app could mint a duplicate stream event after another app overwrote its row). New additive migration **0023** rescopes the `idempotency_keys` PK to `(app_id, tenant_id, replica_id, request_id)` (SQLite + Postgres); `StreamStore.append`'s upsert now targets the app-scoped key and no longer rewrites `app_id` on conflict.
  - **server-storage-3 (Security — cross-app presence eviction):** `presence_leases` PRIMARY KEY omitted `app_id`, letting app B's `set()` overwrite/evict app A's lease at the same `(tenant, presence_type, presence_key)`. Migration **0023** also rescopes the `presence_leases` PK to `(app_id, tenant_id, presence_type, presence_key)`; `PresenceStore.set`'s `ON CONFLICT` targets the app-scoped key.
  - **server-storage-1 (Security — admin audit hash-chain fork):** `AdminAuditStore.record()` read the previous `entry_hash` and inserted in two separate awaited calls with no serialization, so concurrent admin actions chained off the same predecessor and forked the tamper-evidence chain — making `verifyChain()` report a false `{valid:false}` on legitimate concurrency. `record()` now serializes through an in-process mutex and runs the read+insert inside `sql.transaction()`; on Postgres it additionally takes `LOCK TABLE admin_audit_log IN SHARE ROW EXCLUSIVE MODE` for cross-process correctness.
  - **server-storage-4 (Fixed — duplicate signal delivery):** `SignalStore.drain()` did a separate `SELECT` then `DELETE`, so two concurrent drains could both read and return the same rows (at-least-once instead of at-most-once). Replaced with a single atomic `DELETE … RETURNING` (portable across SQLite and Postgres); each row is now claimed by exactly one drain.
  - **server-storage-7 (Fixed/docs — `pruneRetention` blast radius):** Documented that stream-type retention is server-wide by design (FR-145 operator model) and added optional `tenantId`/`appId` fields to `StreamRetentionPolicy` that bound both the age- and count-based DELETE to a single tenant/app when set (omit for the legacy server-wide behaviour).
  - Migrations are strictly additive and safe for existing rows (`app_id` backfilled to `'_default'` by 0021, so single-app deployments are byte-for-byte unaffected); applied in both `migrations.ts` (SQLite) and `pg-framework-migrations.ts` (Postgres). New regression suite `apps/server/tests/storage-audit-fixes.test.ts` (13 tests) fails before / passes after each fix.
- **`frick` (Android SDK) — security & resource-leak hardening of the client (audit findings `native-android-1..5`):**
  - **Security — encryption-at-rest for the session secret (`native-android-1`):** `SQLiteFrickStorage` previously JSON-encoded the entire `FrickSession` — including the bearer `sessionToken` and identity — into a **plaintext** `auth_session` TEXT column, while the docs/commit history claimed the store was "encrypted". It now routes the session secret through an injectable `SessionSecretStore` (new `apps/android/frick/src/main/java/dev/frick/client/FrickSessionSecretStore.kt`); the default is `EncryptedSharedPreferences` over an **AndroidKeyStore** master key (AES-256-GCM at rest — the Android analogue of the iOS Keychain path), wired automatically by `keystoreBackedSessionSecretStore(context)`. The legacy plaintext `auth_session` row is migrated into the encrypted store on first `loadSession()` and **deleted**, so an upgraded install leaves no cleartext token behind. The seam is injectable so the JVM/Robolectric unit tests substitute an `InMemorySessionSecretStore` (no real Keystore needed), mirroring the iOS fake-Keychain pattern. **Honest scope:** only the session **secret** is encrypted; the local **cache** (synced object rows, stream events, pending appends, cache metadata) stays in plain SQLite — it is non-secret. Corrected the overstated "encrypted SQLite store" wording in `FrickSessionManager` / `FrickClient` KDoc and the FR-151 CHANGELOG entry's implication to reflect exactly what is and isn't encrypted.
  - **Security — sign-out now wipes all cached data (`native-android-3`):** `FrickClient.signOut()` cleared the session + pending appends but not the cache, so a prior account's synced records (including records shared with the user by others) survived logout as data remanence on disk. It now also calls `storage.clearCache()`, wiping object rows, stream events, and cache metadata — closing the cross-account leak on shared devices. The demo's `logout()` already rides `signOut()` via `FrickSessionManager`.
  - **Fixed — hung caller coroutines + map leak on disconnect (`native-android-2`):** `FrickSyncSocket.upsertObject()` / `callCommand()` deferreds were only completed by a matching Ack/Nack/CallCommandResult frame, so a write/call in flight when the transport dropped (`onClosed` / `onFailure` / `close()`) left its awaiting coroutine suspended **forever** with no timeout and no error — hanging call-control and object-write flows. All three close paths now drain both pending maps and complete every outstanding deferred with a synthetic "connection closed" failure (`FrickHttpException`, code `sync.reconnectExhausted`). Each request also registers `invokeOnCompletion { pending.remove(requestId) }`, so a cancelled caller (e.g. `viewModelScope` teardown) evicts its entry instead of leaking it for the socket's lifetime.
  - **Fixed (DoS) — bounded msgpack decode (`native-android-4`):** `FrickMsgPack.decodeFrame` pre-sized arrays/maps and read binaries directly from attacker-controlled wire headers and recursed without limit, so a single tiny frame declaring a ~2.1e9-element collection (OOM) or deep nesting (StackOverflow) could crash/wedge the client. The decoder now rejects array/map headers over a cap (`65 536`), binary lengths over 16 MiB, and nesting deeper than 64 with a `DecodeBoundsException` — caught by `onMessage` and surfaced as a `Failed` status rather than destabilizing the process.
  - **Fixed — reconnect now prunes server-side deletions (`native-android-5`):** `FrickObservableStore` folded the post-reconnect snapshot as upserts only, so a row deleted on the server while the client was offline (absent from the snapshot rather than present as a `removed` entry) lingered as a stale "ghost" row indefinitely — potentially resurfacing a revoked-share record. The first delta after each (re)subscribe is now treated as a snapshot boundary that reconciles the cache against the snapshot's id set, pruning absent rows; live deltas after the boundary keep folding in as upserts. The same single-subscription fix is applied to `FrickProjectionStore`. (`FrickCallManager` subscribes to two object types whose snapshots interleave, so a single snapshot-boundary flag is unsafe there; it is left for a per-type follow-up and still drops rows via live `removed` deltas as before.)
  - Regression tests added across `FrickSQLiteStorageTest`, new `FrickClientSignOutTest`, `FrickSyncSocketTest`, `FrickObservableStoreTest`, and `FrickProjectionStoreTest`.
- **`@fricken/server` — auth & SAML audit hardening (SAML `auth/saml.ts` + `storage/saml-assertion-store.ts`; core auth `auth/identity-routes.ts` + `storage/{account-store,refresh-token-store,password-reset-store}.ts`):** Fixed a bundle of confirmed audit findings across the SAML federation seam and the core email-auth / token surface. **SAML:** enforce a signature-algorithm allowlist so weak `rsa-sha1` / SHA1-digest XML-DSIG assertions are rejected before their references are trusted (**auth-saml-1**); treat a malformed `NotBefore`/`NotOnOrAfter` as a hard failure instead of a silently-satisfied bound — `Date.parse` NaN no longer disables the validity window (**auth-saml-2**); evaluate each `<AudienceRestriction>` block individually and require this SP in EVERY block (conjunctive AND across blocks, no flattening), closing the second-restriction bypass (**auth-saml-3**); - **@fricken/server — orphaned-blob GC (FR-57):** Added an **opt-in, off-by-default** recurring job that reclaims `blob_metadata` rows (plus their bytes and derivatives) that no longer have any referencing object. Orphan detection is deliberately conservative and multiply-guarded so it can never delete live user data: **(a) opt-in only** — the `blob.gc` handler and recurring sweep are registered solely when `blobGc.enabled === true`; **(b) grace window** — a blob is eligible only once it is older than `graceMs` (default **7 days**, configurable), so freshly uploaded blobs whose referencing object has not yet been written are always kept; **(c) app `isReferenced(blobId)` hook** — an optional predicate apps supply to protect blobs they reference via untyped fields; a blob is deleted only when unreferenced by **both** the declared-ref scan and the hook; **(d) declared-ref scan only** — the framework-known reference set is computed purely from *declared* blob-ref fields (`kind:'ref'` whose `ref ∈ schema.blobs`) via the new `blobRefFields(schema)` protocol helper. **CAVEAT (read before enabling):** the scan **cannot** see blob ids stored in **untyped `string`/`json` fields** (e.g. a JSON array of attachment blob ids). A session is eligible the moment it expires; embedders can keep a forensics grace window via `createFrickServer({ expiredSessionRetentionGraceMs })` or disable the timer with `expiredSessionPruneIntervalMs: 0` (the one-shot at startup still runs). New `SessionStore.pruneExpired(cutoffIso?)`.
- **`@fricken/server`:** Added an admin session-revocation route `POST /_frick/admin/sessions/revoke` (FR-34), so operators stop deleting `auth_sessions` rows by hand. Revoke by `userId` (every session for that user, optionally scoped to one `tenantId`) or by a single `sessionToken`: the matching rows are deleted (blocking future requests) and any currently-connected WebSocket for those sessions is live-disconnected with close code `1008`, so a revoked client can't keep streaming on an already-open socket. Returns `{ revoked, disconnected }`; a request naming neither target returns `400 sync.protocolError`. Fail-closed audit-logged as `sessions.revoke`. Backed by a new `SyncGateway.closeSessionsForUser(userId, tenantId?)` companion to the existing `closeSession(token)`.
- **`@fricken/server` / `@fricken/protocol`:** Object **deletes** now live-push to subscribed sync clients (FR-142). Previously every other mutation (object upserts, stream appends) fanned out over the sync gateway but `store.deleteObject` did not — so other connected clients kept the deleted row until their next cold refetch. `deleteObject` now emits an `objectDelete` store write-event (only when a row actually existed), which the gateway fans out as a `Delta` frame carrying the removed id two ways: as a tombstone object record (the current Swift/Android SDKs refetch on any object delta and drop the now-absent row) and as a new optional `removed: { type, id }[]` list on `DeltaPayload` (a forward-looking client drops the ids directly, no refetch). Deletes are tenant-scoped and forwarded over the cluster bus (`objectDeletes` envelope) so peer nodes drop the rows for their own subscribers. The `removed` field is additive and absent on deltas with no deletions, so existing clients are unaffected. Retires RangerCRM's `@fricken/server` dist patch for delete fan-out.

### Server — sharing grants cascade to streams + projections

- **`@fricken/server`:** A sharing grant on an object record now cascades READ access to the derived primitives keyed by that record's id, within the same tenant: the stream whose `streamId` equals the granted record id, and the projection rows whose subscribe/read `key` equals that id (FR-70). The cascade runs after the baseline policy + app hooks + object-record grant relaxation and only ever flips a deny to allow (never the reverse); it is strictly read-only (`stream.append` and writes are never relaxed), tenant-scoped, and fails closed when there is no resolvable row id (e.g. a whole-projection subscribe with no `key`). ### Server — encrypted Web Push payloads (RFC 8291)

- **`@fricken/server`:** The Web Push adapter now encrypts notification content per RFC 8291 (Message Encryption for Web Push) using the `aes128gcm` content encoding (RFC 8188), so the title/body/data reach the browser Service Worker instead of an empty wake-up (FR-60). When a `PushSubscription` registration carries the browser's `keys.p256dh` + `keys.auth`, the adapter generates an ephemeral P-256 keypair, derives the shared secret via ECDH, runs the RFC 8291 / RFC 8188 HKDF key + nonce derivation, AES-128-GCM encrypts a single record, and frames the body as `salt(16) || rs(4) || idlen(1) || keyid` + ciphertext with `Content-Encoding: aes128gcm` and `Content-Length` alongside the existing VAPID `Authorization` header. A fresh ephemeral key and salt are used per send; an over-4096-octet body returns `push.payloadTooLarge` without dispatch. Registrations without subscription keys keep the backward-compatible empty-body path. New export `encryptWebPushPayload` from `@fricken/server/push/web-push-adapter`. ### Server — per-record authz on object subscriptions

- **`@fricken/server`:** Object subscriptions are now authorized **per record** (FR-116). A tightening-only policy hook that denies `object.read` for a principal now removes those rows from that subscriber's snapshot and live stream, and a grant on a record makes exactly that record visible to the grantee — so different subscribers on the same object type can see different row sets. ### Server — filesystem blob-bytes driver

- **`@fricken/server`:** Blob bytes can now be stored on the local filesystem instead of SQLite. A new `FRICK_BLOB_DRIVER` selector (mirroring the FR-21 `FRICK_DB_DRIVER` pattern) chooses the blob-bytes backend: `sqlite` (the default, unchanged — bytes stay in the `blob_content` table) or `filesystem` (FR-53). Under the `filesystem` driver, blob bytes are written under `FRICK_BLOB_STORAGE_PATH` in tenant-isolated, id-keyed files; identifiers are hashed into the on-disk path so a crafted blob id can never escape its tenant directory, and one tenant can never read, write, or delete another tenant's bytes. Blob *metadata* always stays in SQLite under either driver, and the blob HTTP route contract is unchanged.
- The `filesystem` driver fails fast at startup: selecting it without a `FRICK_BLOB_STORAGE_PATH` is rejected at config validation, and a path that is not a writable directory is rejected when the driver is constructed. Writes go through a temp-file + atomic rename so a concurrent reader never observes a partial file. New internal storage seam `BlobBytesDriver` (`SqliteBlobBytesDriver` / `FilesystemBlobBytesDriver`) with `write` / `read` / `delete` / `exists`; `BlobStore` gains `deleteContent` / `hasContent`. Object-storage (S3, FR-54), derivatives offload (FR-55), and quotas (FR-56) remain separate follow-ups. See [`docs/operations.md`](docs/operations.md).

- **`@fricken/server`:** Every identity-provider sign-in (Apple, Google, generic OIDC, and email/password) now mints its session with the single configured `FRICK_SESSION_TTL_SECONDS` lifetime instead of a hardcoded 30-day TTL (FR-29). Apps that relied on the old fixed 30-day provider session must set `FRICK_SESSION_TTL_SECONDS` (or `config.sessionTtlSeconds`) explicitly to keep a 30-day lifetime.

When tripped these routes return `429` with a flat `{ "error": "rate_limited", "retryAfterSeconds" }` body and a `Retry-After` header (the existing password routes keep their structured `rateLimit.exceeded` envelope). ### Server — live push for server-originated object/stream writes

- **`@fricken/server`:** Object upserts and stream appends made **server-side** through the store — a background job or app command route calling `store.upsertObject` / `store.upsertObjectWithPolicy` / `store.appendEvent` directly — now live-push to already-subscribed sync clients as `Delta` frames, closing the gap where such writes persisted and updated projections/search but never reached connected subscribers until the slower cursor resync (FR-114). HTTP `PUT /objects/...` writes, which previously did not broadcast at all, now also push live. Deltas remain tenant-scoped (a subscriber only sees writes in its own tenant).
- Broadcasting is now driven by a single funnel: the store emits a write-change notification on every successful object upsert / stream append, and the sync gateway is the sole consumer that fans it out (reusing the same `publishObjects` / `publishStreamEvent` path, including cluster-bus forwarding to peer nodes and the SSE bridge). The gateway frame handlers and the HTTP append route no longer broadcast inline, so a single write produces exactly one delta per subscriber — no duplicates. The broadcast carries the stored (post-merge) object state. New `@fricken/server` exports: `FrickStoreWriteEvent`, `FrickStoreWriteListener`, and `FrickStore.setWriteListener`.
- One observable nuance for a client that writes and is also subscribed: the canonical `Delta` for its own write may now arrive before that write's `Ack` (the broadcast fires inside the store write, ahead of the handler's ack). The two are independent on `@fricken/core` (the delta updates the cache; the ack clears the pending write), so ordering is not contractual and convergence is unaffected. No wire-protocol or `@fricken/core` change. See [`docs/operations.md`](docs/operations.md).

### Server — generic OIDC provider routing

- **`@fricken/server`:** `createFrickServer({ identityProviders })` now accepts an `oidc` array of generic OpenID Connect providers, so apps can plug in any standards-compliant issuer (Okta, Auth0, Microsoft Entra, Keycloak, …) for sign-in alongside the existing Apple / Google / email providers (FR-30). Each provider is `{ id, issuer, clientId, audience?, jwksUri? | discovery, claimMappings? }` and mounts `POST /auth/oidc/:providerId/verify`. The client obtains an `id_token` from the issuer and POSTs it; Frick verifies signature + `iss` + `aud` (defaulting to `clientId`) + expiry with `jose` against the provider's JWKS — resolved either from a directly-configured `jwksUri` or by fetching the issuer's `<issuer>/.well-known/openid-configuration` discovery document (`discovery: true`) and reading its `jwks_uri`. When discovery is used the document's own `issuer` must match the configured issuer (defense against a hijacked well-known endpoint). An optional request `nonce` is checked when supplied. Standard claims (`sub`, `email`, `name`, `preferred_username`) plus any `claimMappings.extra` (`{ "<UserField>": "<claim>" }`) populate the app-owned User object; first sign-in runs the same `onFirstSignIn` hook the other providers use (now `provider: "oidc"` with `providerId`), and a normal bearer session is minted exactly like the Google path. The verified `sub` is stored on the new `oidcSubject` User field as a per-provider composite `"<providerId>:<sub>"`, so two issuers reusing the same subject never alias onto one account. Session TTL/limiter unification across providers remains separate follow-up work (FR-29). New exports: `OidcProviderConfig`, `OidcClaimMappings`, `OidcProviderRuntime`, `VerifiedOidcIdentity`, `VerifyOidcOptions`, `OidcDiscoveryDocument`. No change to Apple, Google, or email behavior. See [`docs/operations.md`](docs/operations.md).

### Server — self-service account deletion

- **`@fricken/server`:** Added an authenticated `DELETE /account` route (with `POST /account` accepted as an alias) that erases the calling principal's OWN account — its owned object records, all of its sessions in the tenant, and its `auth_accounts` row (FR-67). Object deletion reuses the export's ownership convention (`DEFAULT_OWNER_FIELDS` = `ownerId` / `userId` / `createdBy`, override via `AccountDeleteOptions`) and the tenant-scoped store, so another principal's or another tenant's data is never touched — not even a cross-tenant record whose owner field collides with the caller's `userId`. The caller's live gateway connection is closed and the session stops authenticating immediately. Unauthenticated requests return `401`; the `no-store` response reports `accountDeleted`, `deletedSessions`, and per-type `deletedObjects` counts. This is the data-subject "delete my own data" surface, distinct from the operator-driven `/_frick/admin/data-subject` route.
- Apps can cascade product-specific deletion with an `onAccountDelete(principal, result)` hook on `createFrickServer` options; it runs after the framework default commits, receives the framework's result, and owns its own tenant/owner scoping. Every deletion appends an `account.delete` row to the admin audit hash chain. New exports `deleteAccountData` and types `AccountDeleteOptions` / `AccountDeleteResult` / `OnAccountDelete`. Retention policies (soft-delete, legal-hold) remain out of scope (tracked separately). See [`docs/operations.md`](docs/operations.md) and [`docs/threat-model.md`](docs/threat-model.md).

### Server — self-service account data export

- **`@fricken/server`:** Added an authenticated `GET /account/export` route that returns the calling principal's OWN data as a single JSON bundle, grouped by object type, scoped to the principal's tenant (FR-66). A record is included when one of its `ownerId` / `userId` / `createdBy` fields (`DEFAULT_OWNER_FIELDS`) equals the principal's `userId`; tenant isolation is enforced by the tenant-scoped store, so another tenant's records never appear even when an owner field matches. ### Design — token validation hardening

### Server — CORS subdomain/suffix wildcard origins

- `FRICK_ALLOWED_ORIGINS` (and the `allowedOrigins` config override) now accept subdomain wildcard entries of the form `<scheme>://*.<host>` (e.g. `https://*.example.com`) alongside the existing allow-all `*` and exact-origin entries. A wildcard matches any non-empty subdomain prefix over the same scheme and port (`https://app.example.com`, `https://a.b.example.com`) but not the apex host (`https://example.com`) unless that exact origin is also listed. Large multi-tenant deployments no longer need to enumerate every per-tenant origin. Matching is shared by the HTTP preflight/response path and the WebSocket upgrade `verifyClient` check; wildcard-matched requests reflect the concrete request origin (with `Vary: Origin`), never the pattern string. Malformed entries (bare-host wildcards like `https://*`, mid-host wildcards, multiple wildcards, or non-origin strings) are rejected at config load with `FrickConfigError`. The production default remains the closed empty allowlist.

### Server — per-principal connection cap

- `@fricken/server` now enforces a per-principal concurrent WebSocket connection cap in addition to the existing global `maxWebSocketConnections` cap. The new `FrickLimits.maxConnectionsPerPrincipal` field (default `64`) is keyed by `(tenantId, userId)` and enforced at connect when a bearer token is present, otherwise at the `Hello` handshake. Over-cap connections receive a structured `rateLimit.exceeded` Nack (with `details.limit: "maxConnectionsPerPrincipal"`) and are closed with code `1013`, without affecting other principals. Configurable via `createFrickServer({ limits })` or the `FRICK_MAX_CONNECTIONS_PER_PRINCIPAL` env var (an explicit `limits` override wins over the env var). Counters are in-process and reset on restart, consistent with the single-node model.

### Server — outbound email adapter surface

- `@fricken/server` now exports a documented outbound email surface, mirroring the push-adapter convention. New exports from the main entrypoint: the `FrickEmailAdapter` / `FrickEmailMessage` / `FrickEmailDelivery` / `FrickEmailContext` interfaces, `createFrickEmailRouter` (+ `FrickEmailRouter` and its option/helper types), `createFrickResendEmailAdapter` (the Resend reference adapter, reading `RESEND_API_KEY`), and `createFrickTestEmailAdapter` (the in-memory test sink). The Resend adapter is also reachable via the `@fricken/server/email/resend-adapter` subpath, matching `@fricken/server/push/apns-adapter`.
- `identityProviders.email` gained an opt-in `outbound` config (`EmailOutboundConfig`): supply an adapter + `defaultFrom`, and the framework dispatches the password-reset email (`/auth/email/forgot-password`, when a `resetUrl` builder is provided) and a first-sign-in welcome email (`/auth/email/signup`, when `welcome` is set) through it. URL composition stays in app code. Sends are best-effort — a failed delivery is logged and audited in the DevTools event feed but never fails the originating auth request. The existing `onPasswordResetRequested` hook still fires and coexists with framework-managed dispatch, so apps that want full control keep their seam.

### Bug Fixes

- **Swift SDK:** `FrickSyncSocket.sendFrame` now buffers frames into the existing pending queue when the WebSocket task isn't open yet, instead of throwing `notConnected`. This fixes a race where consumers issuing `subscribeObject` / `subscribePresence` / `setPresence` / `clearPresence` / `subscribeProjection` immediately after `FrickClient.connectSync()` (which schedules `openSocket()` on a detached Task) would intermittently fail. Buffered frames flush in FIFO order right after the hello handshake lands.

### Swift SDK — per-app schema hash override

- `FrickClient.init(...)` now accepts a `schemaHash: String` parameter (default `FrickSchema.schemaHash`). Apps with a custom protocol schema can pass their own hash so wire-level guards — response envelopes (`requireCompatibleSchema(expected:)`), the `X-Frick-Schema-Hash` header, the sync Hello frame, and cache-metadata bootstrap — compare against the app's hash rather than the generated foundation default. `FrickSyncSocket.init(...)`, `FrickClientCapabilities.defaultIOS(...)`, and `FrickCacheMetadata.currentSchema(...)` gained matching defaulted `schemaHash:` parameters so the override threads end-to-end. Unblocks RangerCRM (and other consumers) from the previous workaround of aligning their server's `schema.hash` to the foundation hash.

### Swift SDK — auto reset-cache on session swap

- `FrickClient` now auto-resets the on-disk cache when an auth call installs a session for a *different* `userId` than the one currently in the store (RCRM-45). All sign-in / sign-up entry points (`signInWithApple`, `signInWithEmail`, `signUpWithEmail`, `signInWithGoogle`, `signUp`, `login`, `devLogin`) and `restoreSession` funnel through a private `installSession` helper that compares incoming-vs-current `userId` and only clears storage on a real swap. Consumers no longer have to call `resetCache()` before swapping users to avoid the session-scope-mismatch guard; same-user reauth and first-sign-in are unaffected. The helper also clears when this client build's `schemaHash` has drifted from the persisted cache row (a same-`schemaId`/same-revision upgrade `verifyCacheCompatibility` does not catch). Persisted user-scope drift across a process boundary (relaunch, or sign-out → sign-in as a different user) stays the job of `verifyCacheCompatibility`, which `fetchObjects` / `connectSync` run — `installSession` deliberately leaves that metadata intact so the guard can still fire (FR-3).
